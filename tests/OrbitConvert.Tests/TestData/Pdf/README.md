# Owned PDF regression fixture

`arabic-layout.html` is original, synthetic OrbitConvert QA text; it contains no user documents or personal data. `arabic-layout.pdf` is its checked-in selectable-text rendering, authored with installed Microsoft Edge 155.0.0.0 / Chromium Skia PDF, Windows 11. SHA-256: `357A8D68287C95831DF6D3E468F5E1D2D84241BD7A4CF57C1CAF0B90E92F8BD1` (116,653 bytes). Generation is **not** part of test/CI execution and requires no new runtime package.

The three pages cover Arabic-only paragraphs, heading, lam-alef/ActualText, diacritics, lists, wrapped text, parentheses/numbers/punctuation; RTL and LTR mixed lines; a simple three-column table; and an English landscape page with orientation markers. Fonts are embedded subsets of installed Segoe UI, Arial and Times New Roman for rendering this sample, not standalone font distributions or approval to bundle Windows font files. Poppler reference renders of all three pages were visually inspected; actual PDFium PNG output is tested separately.

Optional reproduction: use the installed browser's local HTML-to-PDF facility at A4 with 20 mm margins (the CSS also defines the final landscape page), background graphics enabled and browser headers/footers disabled. No external URLs/resources are used. Browser version/font changes can alter binary bytes, line wraps and metrics; do not regenerate just to make a failing test pass. Check any intentional replacement visually and against Unicode expectations first.

Assertions compare logical Unicode text and code points, not merely Arabic glyph presence or screenshots. Two Arabic cases failed on the pre-fix engine; the English case passed. The corrected implementation must pass all three, the actual structural/PNG operation test and both glyph enumeration-order tests. This fixture is not proof of arbitrary tagged/untagged PDFs, faulty ToUnicode tables, vertical/rotated Arabic, complex columns, every font or universal bidi reversibility. Those remain documented review limitations.
