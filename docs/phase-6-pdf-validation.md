## Backend contract at first checkpoint

- Explicit inspection: read-only source snapshot, strict `%PDF-` identification plus real qpdf check (warnings/recovery rejected), reject **all encrypted PDFs** including empty-password encryption, bounded qpdf JSON action/form/embedded-file screening, independent strict PdfPig parsing and native PDFium page loading/rendering. Returns actual filename, bytes, PDF version, title/author (bounded inert text), page count, effective crop/rotation dimensions and rotation. No password bypass.
- Real qpdf merge preserving requested file/page order; extract page/range; explicit sequence/omission; individual-page split; ascending split-after boundaries. ASCII one-based page grammar; ranges must ascend, invalid/duplicate pages rejected; merge duplicate canonical paths rejected deliberately. Uses verified `--empty --pages <copy> <range> ... -- <candidate>` syntax, never raw PDF byte editing. Structural outputs are not rasterized.
- Reopens every candidate with qpdf/PdfPig/PDFium, compares page count/sequence using parsed graphics-operation SHA-256 plus 36-DPI raster fingerprints/effective dimensions. This is stronger than page-count-only validation, not universal proof of pixel/layout equivalence. Ordinary annotations may be retained, but forms, signatures, active actions and embedded files are rejected; document-level bookmarks/tags/metadata from originals are not promised when starting with `--empty`. No signature-validity guarantee.
- PDFium renders one page at a time to white-background BGRA, then WPF PNG encoding, at 150/300 DPI only. Native crop/rotation dimensions determine allocation/aspect ratio. Magick.NET independently decodes PNGs and verifies actual dimensions. Text uses PdfPig ContentOrderTextExtractor, selected/all pages, strict UTF-8 and bounded real preview; no-text is explicit, never OCR. Arabic/table/multicolumn reading order is not yet verified or claimed.
- All originals stay open read-only with FileShare.Read. Isolated GUID workspaces are reserved with native CreateDirectory (collision never adopted). Single outputs use an owned CreateNew staging file, flush, cancellation check, File.Move(overwrite:false). Multi-output PDF splits/renders require a **new results directory**: deterministic filenames are copied to an exclusively reserved sibling staging directory; one same-parent Directory.Move publishes the complete verified set without replacing anything. Cancellation/copy/finalization collision leaves no published partial set; only exact owned staging/workspace paths are cleaned. A completed directory rename is the commit point; a cancellation arriving afterward cannot undo a complete published result. No directory sweeping.
- PDFium/PdfPig run in short-lived no-window child instances of the existing application via `--pdf-worker`; no new project or alternate process runner. Existing ProcessRunner owns job containment/kill/wait/startup/timeout behavior. Added **optional** job committed-memory quota; existing operations retain default behavior. PDF workers/qpdf use 512 MiB, two-minute stages, one PDF operation at a time. UI integration/busy-close coordination is still pending at this checkpoint.
- Limits: 64 MiB/PDF, 128 MiB aggregate, 20 merge inputs, 200 total pages, 100 output files, 2400-point side, 8192-pixel side, 16 MP/page, 160 MP/render operation, two million text characters, 32 MiB structural JSON, 512 MiB temporary data. Temporary size is polled every 200 ms and can overshoot before termination; not an OS disk quota. Job memory protection begins after confirmed assignment (existing startup gap). Isolation is not a privilege/network sandbox. Native parser faults are contained to a child, not magically made safe; unconfirmed termination and cleanup are explicit.

### Root cause and narrowly scoped fixes

The old PdfPig ContentOrderTextExtractor result already contained reversed Arabic/presentation forms in the saved UTF-8 bytes. It was not caused by WPF rendering or UTF-8 encoding. The PDF's visually ordered glyph stream/ToUnicode/ActualText mapping and extraction order combined to produce the defect. Switching PdfPig UseActualText on alone recovered base Unicode but still reversed words. A real trial of the already bundled PDFium text API also returned inconsistent word order, so it was **not** adopted as a misleading fallback.

`PdfTextReadingOrder` uses PdfPig's official ActualText support only during text extraction, reconstructs horizontal visual lines from glyph baselines, then uses the supported Windows ICU **inverse bidi index map** on atomic glyph replacements. It does not reverse arbitrary strings or split lam-alef/combining/surrogate sequences. PdfPig's zero-advance ActualText mark plus empty-base placeholder is anchored to that base's baseline. Latin/number runs retain their order; simple wide-gap cells are separately reordered and tab-delimited. Non-Arabic pages retain the existing extractor. Source/inspection fingerprints, qpdf/PDFium policies, no-overwrite publication, worker isolation and quotas are unchanged.

No NuGet dependency changed. This PDF-specific correction uses the **OS-supplied ICU C API available on Windows 11**, loaded from System32 only, not downloaded/bundled or resolved beside an input file. Native handles and buffers are local and released in finally; counts, native errors, maps and text sizes are checked inside the existing memory/deadline-bounded worker. Documentation: [Microsoft Windows ICU](https://learn.microsoft.com/en-us/windows/win32/intl/international-components-for-unicode--icu-), [official ICU bidi API / inverse maps](https://unicode-org.github.io/icu-docs/apidoc/released/icu4c/ubidi_8h.html), [PdfPig layout/letter-position API](https://github.com/UglyToad/PdfPig). No custom PDF parser, replacement engine, OCR, dependency upgrade or general architecture rewrite.

Actual Windows language switching also confirmed a blank operation label: after Settings changed the language, the unloaded PDF view could retain SelectedIndex while SelectedItem became null. The focused actual WPF regression reproduced this failure before the fix. Stable localized mode/split Choice objects now update labels without replacing ItemsSource; the same regression passes. ## Native policy initialization-order correction (2026-10-22)

### Confirmed defect and bounded correction

Read the full [Claude diagnosis](https://github.com/abdullahaltalhii1-dev/OrbitConvert-Windows/pull/14#issuecomment-6346587992) before implementing the explicitly owner-authorized fix. At `b519ba1064063fcd61050feaf59172dd25320b9c`, [Push CI](https://github.com/abdullahaltalhii1-dev/OrbitConvert-Windows/actions/runs/39815885494) built with zero warnings/errors but failed one of 476 tests (475 passed, 1 failed, zero skipped): `ImageConversionTests.NativePolicy_BlocksOtherCodersAndEnforcesConfiguredLimits`, Disk expected 0 versus actual 9223372036854775807. [PR CI](https://github.com/abdullahaltalhii1-dev/OrbitConvert-Windows/actions/runs/39815888242) passed 476/0/0. Those contradictory results are historical evidence, not acceptance for this fix.

PDF rendered-page verification previously constructed a native image without the image engine's lazy policy initialization. A new **real PDF-first fresh-process regression failed before production changes**, with the identical unlimited Disk value; its image-first counterpart passed. This reproduces the order defect independently of the suite's randomized class order. No test parallelization was disabled and the existing security test/expected values were not edited.

`MagickRuntime.EnsureInitialized()` now owns a process-wide `Lazy<bool>` with ExecutionAndPublication. Both image processing and PDF rendered-page validation call the gate **before native access**. It loads the same policy, retains 1 MiB profile / 128 MiB single-request limits, verifies all fourteen approved XML rules in order, verifies effective Disk=0, Memory=256 MiB, Width/Height=8192, ListLength=8, Time=30, Thread=1–2 and profile/allocation limits, then probes native **GIF reading and writing must throw policy exceptions**. The PDF reader is explicitly PNG, not content-sniffed. All wildcard coder, delegate/filter, BMP/BMP3 and zero-map restrictions in `ImageMagick/policy.xml` remain unchanged. No package version, engine, workflow or dependency changed.

Missing/invalid policy, native initialization errors, incorrect effective limits or allowed forbidden coder operations poison the gate permanently for that process. It does not try to repair individual getters while coder policy may be absent. Image operations return existing ResourceLimit / OutputValidationFailed results; PDF rendering returns OutputValidationFailed, performs existing owned cleanup and never publishes a candidate. Restart is required after correcting the underlying cause. Source originals and existing no-overwrite staging remain unchanged. The API exposes no effective map/delegate/filter policy getters, so these are preserved by exact loaded XML validation; GIF probes and available getters are **not** a claim of exhaustive native-policy introspection or every-coder security testing.

Sources: pinned [Magick.NET 15.0.0 initialization implementation](https://github.com/dlemstra/Magick.NET/blob/15.0.0/src/Magick.NET/MagickNET.cs), [resource API](https://github.com/dlemstra/Magick.NET/blob/15.0.0/src/Magick.NET/ResourceLimits.cs), [initialization guidance](https://github.com/dlemstra/Magick.NET/blob/15.0.0/docs/Initialization.md). No startup-only/module initializer masks test callers.
